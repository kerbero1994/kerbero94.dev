The system

One API serves three frontends. Everything server-side runs in Docker on a single VPS: infrastructure one person can operate, and the union can pay for.

  1. Clients

    • WebsiteNext.js 16, React Server Components, 8 locales
    • Mobile appExpo, React Native New Architecture, iOS and Android
    • Admin panelReact 19 single-page app on Vite

  2. Delivery

    • NetlifyWebsite and panel, a preview per pull request
    • App Store and Google PlayNative builds, made by hand

  3. API

    • FastAPI, asyncREST v2, with legacy v1 being retired
    • Socket.IOLive chat between members and their advisors

  4. Background work

    • Celery workersSeparate queues: membership imports at three priorities, media ingest
    • SchedulerRecurring and delayed jobs

  5. Data

    • PostgreSQL with pgvectorRecords, plus search for the AI assistant
    • RedisCache, queue broker, rate limits, socket fan-out
    • Object storageS3-compatible, for media and documents

  6. Outside services

    • Firebase Cloud MessagingPush notifications
    • WhatsAppThe publishing bot
    • LLM and translation APIsThe assistant, post drafts, 8 languages
    • SentryErrors on every surface

Why it looks like this

  • Business rules live once, in the API. The frontends render and cache; they don't decide who can see what.
  • Postgres does more than store rows. When the assistant needed search, I added pgvector to the database we already ran instead of a new service to operate. The search case has the details.
  • The cost is a single machine. One VPS is one point of failure, and the CI runner I once put on it competed with production. That story is below.

Five repos, one contract

I kept the API, website, app, panel and shared types in separate repositories, not a monorepo. Each surface ships on its own clock: the website in minutes, the app after store review. What holds them together is the contract.

  1. Pydantic modelsThe API's schemas are the source of truth for every request and response.
  2. JSON Schema bundleA script dumps every model into one deterministic, byte-stable file. A test fails when it's stale.
  3. Shared types packageA versioned npm package with the v2 shapes, endpoints, socket event names and roles.
  4. Three frontendsWebsite, app and panel import the same types, so a breaking change shows up as a type error.

Retiring the legacy API without a rewrite

The union inherited a legacy backend and couldn't go dark while I replaced it. So v2 grows beside v1, and v1 can only shrink: its endpoints are frozen in an inventory, and a test fails if one is added. On the website, features live in v1/ and v2/ folders side by side behind one feature flag; the old folder is deleted once its migration is done.

What it costs

  • Version skew. The package is at 4.0 while the three frontends pin 2.69 to 2.74. A new major is adopted one surface at a time, on purpose, so a contract change never lands everywhere on the same day.
  • Types are mirrored by hand. The TypeScript package follows the schema bundle through a runbook, not a generator. That's the next thing I'd automate.

Frontend architecture

Three React codebases with different jobs, so three different answers to the same questions: where state lives, how data is fetched, and what happens offline.

Website

  • Next.js App Router with React Server Components. No Redux or Zustand: Server Components and per-fetch caching cover most data flows.
  • Feature-sliced layers, with the import direction enforced by ESLint: app, features, shared, infrastructure, lib. Features reach each other only through their public entry point.
  • Eight locales through next-intl, with translation keys type-checked at build time.
  • Accessibility is enforced by lint rules and typed components. The accessibility case shows how.

Mobile app

  • Expo with generated native projects: the ios/ and android/ folders come from config, not from commits. New Architecture, Hermes and the React Compiler.
  • RTK Query for data. The socket only receives; every write goes over HTTP, and server events patch the cache.
  • Offline first: failed writes wait in an encrypted queue and replay on reconnect, only for the account that made them. Sign-in and personal-data writes are never queued.
  • Tokens live in the OS keystore, and personal data is stripped before state is saved to disk.

Admin panel

  • A React 19 single-page app on Vite. API endpoints are injected per feature into a few RTK Query slices.
  • One shared lock for token refresh, so parallel 401s trigger a single refresh. Only idempotent requests are retried.
  • Its own design system, Clay: tokens and components with the same API in every screen.
  • Rebuilt screen by screen. Each screen gets a decision record that describes what exists before anything changes.

Shipping without paid CI

The pipeline I run today wasn't the plan. It's what was left after volume outgrew the budget. I kept the rigor and moved where it runs.

  1. Hybrid CIUntil mid-2026: GitHub-hosted runners for the frontends, a self-hosted runner for the API, cloud builds on top.
  2. Volume jumpsMerged pull requests went from 114 in June to 544 in July. Workflow runs went from 752 to 3,140.
  3. The budget runs outThe monthly Actions budget ran out partway through each month. Jobs were refused without running a step, and new features waited for the next billing cycle.
  4. The runner fights productionThe API's runner lived on the production VPS, with 2 vCPUs. One CI run sat queued for 14 h 44 min.
  5. Decision28 Sep 2026: Actions off in all five repos. Every check moves to the pre-push hook. One workflow stays: the API deploy, which spends no minutes.

The incident that shaped the deploy

That 14-hour queue finished on 29 Jul 2026. The deploy workflow fired three seconds later and built a commit five behind main, then tried to put it on production. A database migration refused it, by luck rather than design. Since then, a guard compares the commit against the real head of main and skips any deploy that's been overtaken. Skipped, not failed: a red mark for a correct outcome teaches people to ignore red marks.

How each surface deploys

  • API. A manual dispatch builds a container image tagged with the commit, pushes it to the GitHub registry, and a self-hosted runner deploys it and runs the Alembic migrations. One deploy at a time, never cancelled midway. Rolling back means deploying an older tag.
  • Website and panel. Netlify builds main, with a preview for every pull request.
  • App. Built by hand on the laptop. QA installs it over the published version, with real data, before it goes to the stores.

What experience bought

The agents write most of the code. Eight years of building frontends is what decides which code is worth writing, and what has to hold when the budget doesn't.

  • Knowing what not to cut. When CI money ran out, the checks moved to the laptop. None of them were dropped.
  • Measuring before deciding. The CI decision came with run counts, queue times and a near-miss deploy, not with a feeling.
  • Picking boring technology one person can run. Postgres, Redis, Docker and one VPS. Nothing that needs a team on call.
  • Writing the reason down. Decision records and guardrails mean every agent session, and the next engineer, starts from the why.

What I'd do differently

  • Set a spending alert before the first cutoff, not after it.
  • Generate the TypeScript types from the schema bundle from day one.
  • Never put a CI runner on the production machine, even for a week.

How this site is built and tested

The same discipline, at the scale of one portfolio. Static HTML with no framework, ten visual styles from one semantic document. Every change goes through a pull request and one gate, and the same gate runs again on exactly what ships before each deploy.

What the gate checks on every change to this site
LayerWhat has to hold
AccessibilityWCAG 2.2 AA with axe on every page in all ten styles, and AAA color contrast (7:1) in every one. Reflow at 320 px, a visible focus ring in every style, reduced motion, Windows high contrast.
End to endPlaywright in Chrome, Firefox, and WebKit (Safari's engine) on an iPhone profile. Any console error or CSP violation fails the run. The site also works without JavaScript.
Visual regression57 screens compared against reviewed baselines.
PerformanceLighthouse on mobile and desktop for every page: performance 95 or more, every other category 100, LCP under 2.5 s, layout shift under 0.1, 800 KB per page at most. Below that, the merge is blocked.
SecurityA Content Security Policy with no unsafe-inline: each inline script and style is allowed by its hash. HSTS, self-hosted fonts, no cookies, and a secrets scan over the whole history.
ContentValid HTML, structured data, and a spell check on everything a visitor reads or hears.

One thing it caught

Lighthouse measured a layout shift of 0.22 on every page. At 412 px wide, a common Android width, the header fit one more item on its first row with the fallback font than with Bodoni, which is 14 px wider. So it re-wrapped when the font arrived and pushed the page down 22 px. Pinning the header layout on narrow screens brought the shift under 0.05 and performance from 88 to 99, and the budget that found it now blocks any change that brings it back.

Production is watched too: a daily smoke test and security-header grade, and Lighthouse against the live site every week.
